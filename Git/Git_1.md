# 1. Введение в систему контроля версий

## Что такое Git и зачем он нужен

**Система контроля версий (Version Control System, VCS)** — это инструмент, который позволяет отслеживать изменения в коде, управлять историей проекта и координировать работу нескольких разработчиков.  
Git — самая популярная распределённая система контроля версий, созданная Линусом Торвальдсом в 2005 году для разработки ядра Linux.

### Основные задачи Git:
- Сохранение полной истории изменений проекта.
- Возможность возврата к любой версии.
- Работа в параллельных ветках без потери изменений.
- Совместная работа команды, в том числе через удалённые репозитории (например, GitHub, GitLab, Bitbucket).
- Минимизация конфликтов при объединении кода.

## Отличия от централизованных систем (SVN, CVS)

Ранее популярные системы контроля версий (CVS, Subversion/SVN) работали по централизованной модели:
- Все данные хранились на сервере.
- Локально у разработчика была только рабочая копия файлов.
- Для многих операций (просмотр истории, создание ветки) требовалось подключение к серверу.

Git решает эти проблемы:

| Особенность             | Централизованные (SVN, CVS)       | Git (распределённый) |
|--------------------------|------------------------------------|-----------------------|
| Хранение истории        | На центральном сервере            | У каждого разработчика полный клон |
| Работа оффлайн           | Почти невозможна                   | Полный функционал доступен локально |
| Создание веток           | Тяжёлая операция                   | Очень быстро и легко |
| Скорость операций        | Зависит от сети                   | Максимально высокая (локальные данные) |
| Отказоустойчивость       | Потеря сервера = потеря истории   | История есть у каждого разработчика |

Таким образом, Git более гибкий, быстрый и надёжный.

## Распределённая архитектура Git

- Каждый разработчик имеет **полный клон репозитория**, включая всю историю.
- Есть **локальный репозиторий** (на компьютере разработчика) и **удалённый репозиторий** (например, на GitHub).
- Обмен изменениями происходит через команды `git push` (отправка изменений) и `git pull` (получение и объединение).
- При необходимости можно работать полностью оффлайн, а затем синхронизироваться.

## Основные понятия

- **Репозиторий (repository)** — хранилище проекта, включающее файлы, историю изменений и метаданные (папка `.git`).
- **Коммит (commit)** — зафиксированное изменение состояния проекта. У каждого коммита есть хеш, автор, дата и сообщение.
- **Ветка (branch)** — независимая линия разработки. Основная ветка обычно называется `main` или `master`.
- **HEAD** — указатель на текущую ветку или коммит.
- **Staging area (индекс)** — промежуточная область, где готовятся изменения перед коммитом.

# 2. Установка и настройка Git

## Установка на разные ОС

### Linux
На большинстве дистрибутивов Git можно установить из официальных репозиториев:

```bash
# Debian/Ubuntu
sudo apt update
sudo apt install git

# Fedora
sudo dnf install git

# Arch Linux
sudo pacman -S git
```

### macOS
1. Установить через Homebrew:
   ```bash
   brew install git
   ```
2. Либо установить [Xcode Command Line Tools](https://developer.apple.com/xcode/), где Git идёт по умолчанию:
   ```bash
   xcode-select --install
   ```

### Windows
1. Скачать [официальный установщик Git for Windows](https://git-scm.com/download/win).
2. Во время установки можно выбрать:
   - текстовый редактор по умолчанию (например, Vim или Notepad++).
   - интеграцию с PowerShell или Git Bash.
   - добавление `git` в переменную PATH.

Проверка установки:
```bash
git --version
```

## Первоначальная настройка

Перед началом работы нужно настроить имя пользователя и email. Эти данные будут попадать в каждый коммит.

```bash
git config --global user.name "Your Name"
git config --global user.email "email@example.com"
```

Также можно задать редактор по умолчанию (например, Vim, Nano или VS Code):

```bash
git config --global core.editor "vim"
# или
git config --global core.editor "code --wait"
```

Настройка цвета для удобного чтения вывода:
```bash
git config --global color.ui auto
```

## Просмотр настроек

Чтобы увидеть текущие настройки Git, выполните:

```bash
git config --list
```

Можно проверить значение конкретного параметра:

```bash
git config user.name
git config user.email
```

# 3. Создание и клонирование репозиториев

## Инициализация нового репозитория: `git init`

Команда `git init` используется для создания нового локального репозитория Git в существующей папке. После её выполнения в директории появляется скрытая папка `.git`, где Git хранит всю историю, объекты и настройки.

```bash
# Создать новый репозиторий в текущей папке
git init

# Создать новый репозиторий в указанной папке
git init my_project
```

После инициализации можно добавлять файлы (`git add`) и создавать коммиты (`git commit`).

---

## Клонирование существующего репозитория: `git clone <url>`

Команда `git clone` создаёт локальную копию существующего удалённого репозитория (например, с GitHub, GitLab или Bitbucket).

```bash
# Клонирование по HTTPS
git clone https://github.com/user/repo.git

# Клонирование по SSH
git clone git@github.com:user/repo.git

# Клонирование в папку с другим именем
git clone https://github.com/user/repo.git my_project
```

При клонировании Git автоматически создаёт:
- Папку проекта с рабочими файлами.
- Папку `.git` с историей.
- Настройку удалённого репозитория `origin`.

---

## Структура папки `.git`

Папка `.git` хранит все данные репозитория. Основные элементы:

- **HEAD** — ссылка на текущую ветку.
- **config** — настройки репозитория (локальные параметры).
- **refs/** — ссылки на ветки и теги.
- **objects/** — объекты Git: коммиты, деревья (структуры каталогов), блобы (файлы).
- **hooks/** — скрипты, выполняемые при определённых событиях (например, pre-commit).
- **logs/** — история перемещений ссылок (например, `HEAD`).

Обычно папка `.git` скрыта и изменяется только через команды Git.

---

## Статус репозитория: `git status`

Команда `git status` показывает текущее состояние репозитория:
- В какой ветке находится пользователь.
- Какие изменения добавлены в индекс (staged).
- Какие изменения не отслеживаются (untracked).
- Какие изменения есть в рабочей директории.

Пример:
```bash
git status
On branch main
Your branch is up to date with 'origin/main'.

Changes not staged for commit:
  modified:   file.txt

Untracked files:
  new_file.txt
```

Полезные опции:
- `git status -s` — короткий формат (например, `M file.txt`, `?? new_file.txt`).
- `git status -b` — показывает текущую ветку и её связь с удалённой.

# 4. Базовый workflow: add, commit, push

## Добавление файлов в staging area: `git add`

Команда `git add` добавляет изменения в **staging area** (индекс), чтобы они попали в следующий коммит.

```bash
# Добавить один файл
git add file.txt

# Добавить все файлы
git add .

# Добавить все изменённые файлы, но не новые
git add -u
```

Важно: `git add` не делает коммит, а только подготавливает изменения.

---

## Создание коммита: `git commit -m "message"`

Фиксирует изменения из staging area в истории репозитория.

```bash
git commit -m "Добавил новую функцию"
```

Советы:
- Сообщение должно быть коротким и информативным.
- Для больших изменений рекомендуется использовать многострочные сообщения:

```bash
git commit
# Откроется редактор, где можно ввести заголовок и описание.
```

---

## Просмотр истории коммитов: `git log`

Команда `git log` показывает список коммитов в текущей ветке.

Примеры:
```bash
# Полный лог
git log

# Краткий однострочный лог
git log --oneline

# Граф ветвлений
git log --oneline --graph --all --decorate
```

---

## Отправка изменений на сервер: `git push`

После создания коммитов локально их нужно отправить в удалённый репозиторий.

```bash
# Отправить изменения в удалённый репозиторий
git push origin main
```

Если ветка новая, нужно добавить ключ `-u`, чтобы связать локальную ветку с удалённой:

```bash
git push -u origin feature-branch
```

После этого достаточно писать `git push` без параметров.

# 5. Основные команды статуса и истории

Этот раздел подробно описывает команды Git, которые помогают отслеживать состояние репозитория и историю изменений: `git status`, `git log`, `git diff`, `git show`, а также дополнительные полезные команды для анализа истории (`git blame`, `git shortlog`, `git reflog`, `git bisect`).

---

## git status — текущее состояние

`git status` показывает текущее состояние рабочей директории и индекса (staging area). Это первая команда, которую полезно вызывать перед любыми операциями с коммитами или пушем.

### Что показывает `git status`

- Текущая ветка и её связь с удалённой (например: "Your branch is ahead of 'origin/main' by 2 commits").
- Файлы, подготовленные к коммиту (staged) — секция **Changes to be committed**.
- Изменённые файлы, но не добавленные в индекс — **Changes not staged for commit**.
- Ненаблюдаемые (untracked) файлы — **Untracked files**.

### Полезные форматы и флаги

- Короткий формат (summary):

```bash
git status -s
# или
git status --short
```

Вывод будет компактным: `M` — modified, `A` — added, `??` — untracked и т.д.

- Машиночитаемый формат (для скриптов):

```bash
git status --porcelain
# v2:
git status --porcelain=v2
```

- Показать и ветку в кратком виде:

```bash
git status -sb
```

### Типичные действия после `git status`

- Добавить файл в индекс: `git add file`.
- Убрать из индекса (оставив изменения в рабочей директории): `git restore --staged file` или `git reset HEAD file`.
- Отменить локальные изменения (сброс к версии в HEAD): `git restore file`.

### Советы и предостережения

- Используйте `--porcelain` в скриптах, так как формат стабильный и предсказуемый.
- Не игнорируйте сообщения о расхождении с удалённой веткой — сначала `git fetch`, затем `git status`/`git log`.

---

## git log — история коммитов

`git log` показывает историю коммитов. Очень гибкая команда с множеством опций для фильтрации и форматирования вывода.

### Базовые примеры

```bash
# Полный лог
git log

# Однострочный компактный лог
git log --oneline

# Граф ветвлений
git log --oneline --graph --decorate --all

# Показать изменения (патч)
git log -p

# Показать статистику изменения файлов
git log --stat
```

### Фильтрация по времени, автору, пути

```bash
# Коммиты за последние 2 недели
git log --since="2 weeks ago"

# Коммиты определённого автора
git log --author="Ivan"

# История конкретного файла (с отслеживанием переименований)
git log --follow -- path/to/file
```

### Форматирование вывода

```bash
# Настроить формат: короткий хеш, автор, дата и сообщение
git log --pretty=format:"%h %an %ad %s" --date=short
```

Полезные форматы (`--pretty`): `%H` (полный хеш), `%h` (короткий хеш), `%an` (имя автора), `%ae` (email автора), `%ad` (дата), `%s` (сообщение).

### Практические советы

- Для быстрого обзора используйте `--oneline --graph --decorate --all`.
- При поиске виновного патча можно комбинировать `git log -S"text"` (поиск по добавлению/удалению текста) и `git log -G"regex"` (поиск по регулярному выражению в патче).

## git diff — сравнение изменений

`git diff` показывает различия (diff) между состояниями репозитория: рабочей директорией, индексом и коммитами.

### Основные случаи использования

- Изменения в рабочей директории относительно индекса (то, что ещё не добавлено в staging):

```bash
git diff
```

- То, что уже добавлено в индекс относительно последнего коммита (то, что попадёт в следующий коммит):

```bash
git diff --staged
# или
git diff --cached
```

- Различия между двумя коммитами или ветками:

```bash
git diff commit1 commit2
git diff branchA..branchB
# отличие: git diff A..B равносильно git diff A B
```

- Сравнить текущую ветку с удалённой:

```bash
git fetch origin
git diff origin/main..HEAD
```

### Полезные флаги

- `--name-only` — показать только список файлов.
- `--stat` — компактная статистика изменений по файлам.
- `-w` — игнорировать изменения в пробелах.
- `-U<n>` — количество контекстных строк вокруг изменений.
- `--word-diff` — показать изменения на уровне слов.
- `--color-words` — цветное выделение изменений слов.

### Инструменты для просмотра diff

- `git difftool` — открывает изменения в внешнем diff-редакторе (если настроено), удобно для визуального сравнения.

### Советы

- Перед коммитом всегда смотрите `git diff --staged`, чтобы убедиться, что в коммит попали именно те изменения, которые вы хотели.
- При сложных слияниях `git diff` помогает понять причины конфликтов.

## git show — информация о конкретном коммите

`git show` отображает данные о заданном коммите: метаданные и патч.

### Примеры использования

```bash
# Показать последний коммит
git show HEAD

# Показать конкретный коммит по хешу
git show 9fceb02

# Показать только список файлов, изменённых в коммите
git show --name-only <commit>

# Показать только сообщение коммита (body)
git show --no-patch --format=%B <commit>

# Показать содержимое файла в данном коммите
git show <commit>:path/to/file
```

### Полезные флаги

- `--pretty` для форматирования вывода (как в `git log`).
- `--name-only` / `--name-status` для списка файлов.
- `-p` (по умолчанию) — показать патч.

### Когда использовать

`git show` удобно, когда нужно изучить конкретный коммит — кто сделал, когда и какие строки/файлы были изменены. Также полезно для извлечения старой версии файла.

## Дополнительные команды для анализа истории

### git blame — кто и когда изменил строки в файле

Показывает, какой коммит и автор отвечает за каждую строку файла.

```bash
git blame path/to/file
# Диапазон строк
git blame -L 1,120 path/to/file
# Показать email автора
git blame -e path/to/file
```

**Применение:** поиск того, кто внёс определённое изменение, и понимание контекста изменения.

### git shortlog — статистика по авторам

Короткая статистика по коммитам, сгруппированная по авторам.

```bash
# Суммарно по авторам
git shortlog -s -n
# С email
git shortlog -s -n -e
```

Полезно при подготовке отчётов о вкладе команды.

### git reflog — история перемещений HEAD

`git reflog` показывает локальную историю перемещений `HEAD` (включая изменения, не попавшие в лог). Очень полезно для восстановления «потерянных» коммитов.

```bash
git reflog
# Восстановление состояния по записи reflog
git reset --hard HEAD@{3}
```

**Важно:** reflog — локальная вещь, не реплицируется на удалённый репозиторий.

### git bisect — бинарный поиск проблемного коммита

`git bisect` помогает найти коммит, который ввёл ошибку, за O(log N) шагов, путём автоматизации последовательных проверок "good/bad".

Простой сценарий:

```bash
git bisect start
git bisect bad            # текущий (плохой) коммит
git bisect good v2.0.0    # известный хороший тег/коммит
# Далее Git будет указывать на коммиты для проверки
# После нахождения:
git bisect reset
```

## Краткая шпаргалка (cheat sheet)

```text
# Быстро проверить состояние
git status -sb

# Короткий граф истории
git log --oneline --graph --decorate --all

# Показать, что будет в следующем коммите
git diff --staged

# Показать незакоммиченные изменения
git diff

# Информация о коммите
git show <commit>

# Кто редактировал строки файла
git blame -L start,end path/to/file

# Восстановление потерянных состояний
git reflog
git reset --hard HEAD@{N}

# Поиск проблемного коммита
git bisect start

```
